The essence of a document

Content becomes a document when it can be trusted across time.

A document is a bounded cognitive snapshot. It carries not only what is known, but where that knowledge applies, what supports it, who or what produced it, and how it has changed.

DOCUMENT =

Content + Context
+ Evidence + Identity
+ History

IMPORTANT DISTINCTION
Text communicates. A document remains addressable, interpretable, and accountable after its author is gone.
01 / TEXT

Says something

Useful language, but no durable boundary, provenance, or lifecycle.

02 / DATA

Structures something

Machine-readable fields, but structure alone does not establish trust.

03 / DOCUMENT

Can be relied upon

A named, scoped, evidenced, and versioned assertion that others can inspect.

FactLineage's core value

Verified understanding that survives the session.

FactLineage is not a chat archive and not another folder of prose. It is a version ledger for project understanding, designed so the next agent can inherit what was learned without inheriting blind trust.

Code stays the source of truth. FactLineage preserves the verified interpretation needed to act on it.

01

Carry understanding forward

Turn analysis that would disappear with a context window into durable project knowledge.

02

Keep trust inspectable

Every code-related conclusion can point back to a repository, commit, file, symbol, and line range.

03

Preserve change, not just state

Append immutable revisions so an agent can see how understanding evolved and why.

04

Retrieve only what the task needs

Use exact terms and semantic intent to recover focused context instead of rereading the repository.

Project knowledge record

Five parts make understanding reusable.

The useful unit is not a page. It is a claim package: a conclusion with an explicit scope, supporting evidence, provenance, and an append-only history.

01 / CLAIM

What is understood

A concise assertion about a feature, API, behavior, or design decision.

02 / SCOPE

Where it applies

The owning project, version, branch, module, and relevant constraints.

03 / EVIDENCE

Why it is credible

Concrete code locations and Git context that let another agent verify it.

04 / PROVENANCE

How it came to be

The author or agent, creation time, and basis of the interpretation.

05 / HISTORY

How it evolved

Immutable revisions that retain earlier understanding instead of overwriting it.

Knowledge lifecycle

From code fact to the next verified action.

FactLineage closes a loop: understand the code, verify the claim, preserve it with evidence, retrieve it by task intent, and revalidate it when the project changes.

STEP 01

Understand

An agent identifies a behavior, contract, or decision in the repository.

STEP 02

Verify

File, symbol, line, project boundary, and Git state are checked.

STEP 03

Preserve

The claim and evidence become an immutable knowledge version.

STEP 04

Retrieve

Keyword and semantic search recover the smallest relevant context.

STEP 05

Revalidate

The next agent follows the evidence, acts, and appends the new verified state.

What changes for an agent

Less reconstruction. More accountable progress.

The agent does not skip verification. It starts from a stronger position: prior understanding is discoverable, bounded, and connected to the exact source that must be checked.

01 / FOCUS

Smaller context footprint

Load a focused record first, then inspect only the source needed for the task.

02 / SPEED

Less repeated discovery

Reuse verified architecture, contracts, and implementation locations across sessions.

03 / SAFETY

Defensible changes

Ground plans and edits in evidence and preserve why the understanding changed.

04 / CONTINUITY

Durable handoffs

Transfer project knowledge between agents without reducing it to a chat transcript.
